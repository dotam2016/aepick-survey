## 2. 아키텍처 방향 (확정: 하이브리드)

**Android 네이티브 쉘 + 웹 콘텐츠(WebView)** 구조를 채택한다.

```
[Android Shell (Kotlin)]          ← 2차 단계에서 제작
 ├─ Lock Task Mode (키오스크 잠금)
 ├─ WebView (전체화면)
 ├─ 카메라 권한 브릿지
 └─ 기기 상태 리포팅
        │
        ▼
[Kiosk Web App (React SPA)]       ← 1차 프로토타입에서 제작
 ├─ 17개 화면 · 6개 게임 · 촬영(getUserMedia)
 └─ 백엔드 API 통신
        │
        ▼
[Backend API] ── [AI Image Worker] ── [Storage]
        │
        ├─ [모바일 결과 웹]  ← QR 스캔 진입
        └─ [운영자 대시보드]
```

**채택 이유**
- 체험 콘텐츠(화면·게임·애니메이션)는 웹 기술로 개발해 **PC 브라우저에서 즉시 개발·테스트** 가능
- 프로토타입 단계에서는 태블릿의 Chrome 전체화면(또는 키오스크 브라우저)만으로 시연 가능
- 현장 배포 단계에서 Android 쉘을 추가해 Lock Task Mode, 자동 복구, 기기 모니터링 확보
- 카메라는 WebView의 `getUserMedia`로 처리하고, 품질검사(얼굴 위치·밝기)는 웹 레이어에서 수행

### 2.1 기술 스택 (프로토타입)

| 영역 | 선택 | 비고 |
|---|---|---|
| 키오스크 앱 | React + TypeScript + Vite | 세로형 1200×1920 기준, 터치 최적화 |
| 애니메이션 | Framer Motion + CSS/Canvas | DNA 젬·리빌 연출 |
| 촬영/품질검사 | getUserMedia + MediaPipe Face Detection(웹) | 얼굴 1명·크기·밝기 확인 |
| 백엔드 | Node.js + Fastify + TypeScript | 프론트와 언어 통일로 개발 속도 확보 |
| DB | SQLite(프로토) → PostgreSQL(배포) | ORM(Drizzle/Prisma)으로 마이그레이션 대비 |
| 이미지 처리 | sharp + node-canvas | 템플릿 합성(프레임·그래프·로고) |
| AI 이미지 | 목업(템플릿 합성) → 실API 교체 | 어댑터 인터페이스로 추상화 |
| 결과 웹 | 백엔드가 서빙하는 모바일 반응형 페이지 | `/r/{token}` |
| 대시보드 | React (kiosk와 모노레포 공유) | `/admin` |
| QR 생성 | 서버 생성 (qrcode 라이브러리) | |
| Android 쉘 | Kotlin + WebView (2차) | Lock Task Mode |

> 기획안의 FastAPI/PostgreSQL/Redis/S3 구성은 **배포 단계 아키텍처**로 유지하되,
> 프로토타입은 단일 Node 서버 + SQLite + 로컬 파일 저장으로 단순화한다.
> AI 이미지 잡 큐는 프로토타입에서 인메모리 큐로 구현하고 인터페이스만 동일하게 유지한다.

### 2.2 저장소 구조 (모노레포)

```
aepick-beauty-dna/
├── apps/
│   ├── kiosk/          # 키오스크 체험 앱 (React SPA)
│   ├── result-web/     # 모바일 결과 페이지
│   └── admin/          # 운영자 대시보드

├── android-shell/      # (2차) Kotlin WebView 쉘
```

## 4. Beauty DNA 체계

### 4.1 6축 스코어링

각 게임의 선택을 해당 축 0~100점으로 환산. (세부 산식은 기능정의서에서 확정)

| 축 | 소스 게임 | 의미 |
|---|---|---|
| Repick | CORE1 | 지속적 만족·재구매 |
| Value | CORE2 | 가격 대비 가치 |
| Care | CORE3 | 성분·안전·정보 신뢰 |
| Trend | CORE4 | 트렌드 수용성 |
| Local Fit | CORE5 | 현지 기후·생활 적합 |
| Trust | CORE6 | 리뷰·사회적 증거 |

### 4.2 페르소나 판정

상위 2개 축 조합으로 6유형 판정 (동점 규칙은 기능정의서에서 정의):

Loyal Glow Keeper / Smart Beauty Curator / Trend Muse / Local Beauty Expert / Trust Guardian / Beauty Explorer

- 15개 축 조합(6C2) 전부에 대해 유형 매핑 테이블을 정의해 **어떤 조합도 결과가 비지 않게** 한다.
- 낮은 축은 언급하지 않고 상위 2축을 강점으로 서술한다.

## 5. AI 이미지 전략 (확정: 목업 → 실API)

**Phase A — 템플릿 합성 (프로토타입 기본)**
- 원본 사진 + DNA 컬러 배경 + AEPICK 프레임 + 유형명 + 6축 그래프 + 해시태그를 서버에서 합성
- 이것이 곧 기획안 11장의 "생성 실패 폴백"이므로, 폴백 경로를 먼저 만들고 검증하는 효과

**Phase B — 생성형 API 연동**
- `ImageGenerator` 인터페이스 뒤에 실제 이미지 생성 API(예: Gemini 이미지 모델) 어댑터 추가
- 얼굴 정체성 유지 + DNA 기반 배경·조명·무드 생성
- 로고·텍스트·그래프는 항상 Phase A 합성 엔진이 후처리 (AI 텍스트 오류 방지)

**폴백 정책 (기획안 11장 준수)**
1. 정상: 생성 이미지 + 그래픽 합성 노출
2. 지연(>20초): 리빌 애니메이션 연장 → 초과 시 QR 선발급, 결과웹에서 완성본 확인
3. 실패: 즉시 Phase A 템플릿 결과 제공 — 체험은 항상 끝까지 완료
