> 버전 2.0 · 2026-08-19 · 상태: 구현 반영 완료
> 하노이 팝업 **Core Value Zone** 운영 스펙 기준 서비스 기획

## 0. v1에서 무엇이 바뀌었나

v1은 **사진을 찍어 AI 이미지를 만들어 주는 체험**이었다.
v2는 팝업 운영 스펙이 확정되면서 **앱 회원과 연결되고 제품 투표로 이어지는 체험**으로 바뀌었다.

| 구분 | v1 | v2 |
|---|---|---|
| 고객 식별 | 익명 | **aepick 앱 계정** (QR 페어링) |
| 사진 촬영 | 있음 | 없음 |
| AI 이미지 생성 | 있음 | 없음 |
| 결과물 | 개인화 이미지 | **맞춤 브랜드·제품 추천** |
| 체험 후 | 종료 | **브랜드 체험 → 제품 투표 → 사은품** |
| 브랜드 관리 | 코드 상수 7개 | **어드민 화면에서 관리, 10개** |
| 기기 | 1대 | **10대 규모** |

**이 변화의 의미**

- 익명 체험이 아니라 **회원 데이터에 귀속**되므로 재방문 추적과 후속 마케팅이 가능해졌다
- 얼굴 사진을 다루지 않게 되어 **개인정보 부담과 기술 리스크가 크게 줄었다**
- 체험이 **팝업 전체 동선의 입구**가 되었다 — 추천으로 브랜드 부스로 보내고, 투표로 회수한다

## 1. 프로젝트 정의

| 항목 | 내용 |
|---|---|
| 프로젝트명 | AEPICK BEAUTY DNA — Six Picks. One Beauty Identity. |
| 형태 | 팝업스토어 Core Value Zone의 태블릿 체험 + 모바일 후속 페이지 |
| 하드웨어 | **안드로이드 PAD 약 10대** |
| 체험 시간 | 1인당 약 4분 |
| 대상 지역 | 베트남 하노이 (베트남어 기본 / 영어 / 한국어) |

### 1.1 팝업 전체 동선에서의 위치

```
① 입장   고객이 aepick 앱 다운로드·가입          ← 우리 범위 밖
② 체크인 Core Value Zone 입장
③ 체험   PAD의 QR 스캔 → 6게임 → Beauty DNA      ← ★ 우리 범위
④ 추천   결과 QR → 모바일에서 맞춤 브랜드 확인    ← ★ 우리 범위
⑤ 회유   팝업 공간에서 브랜드·제품 직접 체험
⑥ 투표   직원 안내 → 제품 3개 투표               ← ★ 우리 범위
⑦ 보상   직원 확인 후 사은품 지급
```

**체험은 목적이 아니라 장치다.** 고객을 브랜드 부스로 보내고(④), 체험한 결과를 투표로 회수한다(⑥).

### 1.2 구현 범위

| # | 구성요소 | 상태 |
|---|---|---|
| ① | PAD 체험 앱 | 완료 — 14화면, 6게임, 페어링 |
| ② | 백엔드 API | 완료 — 페어링·세션·결과·투표·카탈로그 |
| ③ | 모바일 결과·투표 웹 | 완료 |
| ④ | 운영자 대시보드 + **카탈로그 관리** | 완료 |

**목업으로 남은 것은 aepick 앱 연동 한 곳뿐이다.** 앱 팀과 협의가 끝나면 어댑터만 교체하면 된다.

## 2. 아키텍처

```
[PAD ×10 — Chrome 또는 WebView]
 └─ Kiosk Web App (React SPA)
        │  페어링 폴링 / 게임 답변 / 완료
        ▼
[Backend  Node + Fastify  단일 프로세스·단일 포트]
 ├─ /            PAD 키오스크 (정적 빌드 서빙)
 ├─ /p/:code     페어링 착지        ← 앱이 대체할 자리
 ├─ /r/:token    모바일 결과
 ├─ /v/:token    제품 투표
 └─ /admin       대시보드 · 카탈로그 관리
        │
        ▼
   [DB]  현재 node:sqlite → 운영 시 PostgreSQL
```

**단일 포트로 통일한 이유**: 현장에서 관리자가 다뤄야 할 주소가 하나뿐이고,
QR 주소가 접속한 호스트에서 그대로 유도되어 네트워크 환경이 바뀌어도 손댈 곳이 없다.

### 2.1 기술 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| PAD 앱 | React + TypeScript + Vite | 세로형 1200×1920 기준 |
| 애니메이션 | Framer Motion | ⚠️ `AnimatePresence` 미사용 — 3장 참고 |
| 백엔드 | Node 22 + Fastify 5 | 프론트와 언어 통일 |
| DB | **`node:sqlite`** → PostgreSQL | 네이티브 빌드 의존성 없음. 실험적 API라 이관 필요 |
| 결과·투표 웹 | 서버가 서빙하는 모바일 HTML | 별도 프론트 빌드 없음 |
| QR 생성 | 서버 (qrcode) | |
| 테스트 | vitest 37개 | 채점·페르소나·i18n 정합성 |

> v1에 있던 **sharp(이미지 합성)와 Gemini(AI 생성) 의존성은 제거**했다.
> 서버 사양 요구와 장애 지점이 함께 줄었다.

### 2.2 저장소 구조

```
apps/kiosk/          PAD 체험 앱
server/              API + 결과·투표·어드민 페이지
packages/shared/     타입 · 채점 로직 · 페르소나 · i18n
docs/                기획 · 기능정의 · API · 검증 · 가이드
```

## 3. 사용자 여정 (14화면)

```
S00 대기화면(페어링 QR) ──[고객이 QR 스캔]──> S01 언어선택 → S05 안내
→ S06~S11 게임 6종 (사이사이 브릿지) → S12 DNA 분석
→ S13 DNA 결과 → S15 QR·추천 → S16 종료 → S00

[모바일]  결과 페이지 → 투표 → 투표 완료(직원 확인)
```

| 화면 | 이름 | 핵심 요소 | 목표 시간 |
|---|---|---|---|
| S00 | Attract | **페어링 QR**, 누적 참여자, 인기 DNA | 대기 |
| S01 | 언어 선택 | vi(기본)/en/ko | 5초 |
| S05 | Core Value 안내 | 6개 여정 소개 | 10초 |
| S06 | CORE1 Empty Bottle Challenge | 카드 넘기기 → REPICK 드래그 | 30초 |
| S07 | CORE2 Beauty Budget | 코인 10개 드래그 배분 | 35초 |
| S08 | CORE3 Beauty Shield | 10초 제한, 8카드 중 3개 탭 | 25초 |
| S09 | CORE4 Next Beauty Wave | 6카드 3방향 스와이프 | 30초 |
| S10 | CORE5 Hanoi Weather Lab | 상황 + 5쌍 속성 조합 | 35초 |
| S11 | CORE6 Review Detective | 리뷰 3종 중 선택 | 25초 |
| SB | 브릿지 ×6 | 축별 브랜드 메시지 (자동 3초) | 18초 |
| S12 | DNA 분석 | 젬 회전 연출 | 3.5초 |
| S13 | DNA 결과 | 유형명·키워드·레이더 차트 | 15초 |
| S15 | QR·추천 | **결과 QR**, 추천 브랜드 | 30초 |
| S16 | 종료 | 마무리 이미지 → 초기화 | 8초 |

### 3.1 설계상 중요한 두 가지

**① 페어링 QR은 체험 1회마다 새로 발급된다**

PAD에 고정 QR을 붙여 두면 두 사람이 비슷한 시각에 찍었을 때 서버가 **어느 PAD의 체험자인지 판별할 수 없다.**
그래서 대기화면이 매번 일회용 코드를 발급하고, 클레임되는 즉시 소각한다.
PAD 10대가 동시에 돌아가는 환경에서 이것이 없으면 세션이 섞인다.

**② 종료 QR은 대체 불가능하다**

고객은 입장 시 페어링한 뒤 **폰을 주머니에 넣는다.** 체험이 끝나는 시점에 폰 화면을 자동으로 띄울 방법이 없다.
따라서 종료 화면의 QR이 고객을 다시 폰으로 부르는 유일한 수단이다.

다만 페어링을 했기 때문에 이 QR은 익명 QR보다 강하다 — 스캔 즉시 **로그인 없이** 본인 결과가 열리고,
QR을 찍지 않고 가버린 고객도 **나중에 앱에서 결과를 되찾을 수 있다.**

### 3.2 개발 시 주의 (실제 겪은 문제)

**`AnimatePresence`를 쓰지 않는다.** exit 애니메이션이 끝나지 않으면 이전 화면이 언마운트되지 않고
DOM에 누적되어, **이전 화면의 타이머와 토스트가 살아남아 다음 게임에서 오작동**한다.
v1 검증 중 실제로 발생해 제거했다.

## 4. Beauty DNA 체계

v1과 동일하다. 채점 로직과 페르소나 정의는 바뀌지 않았다.

### 4.1 6축 스코어링

| 축 | 소스 게임 | 의미 |
|---|---|---|
| Repick | CORE1 | 지속적 만족·재구매 |
| Value | CORE2 | 가격 대비 가치 |
| Care | CORE3 | 성분·안전·정보 신뢰 |
| Trend | CORE4 | 트렌드 수용성 |
| Local Fit | CORE5 | 현지 기후·생활 적합 |
| Trust | CORE6 | 리뷰·사회적 증거 |

### 4.2 페르소나 판정

상위 2개 축 조합으로 6유형 판정:

Loyal Glow Keeper / Smart Beauty Curator / Trend Muse / Local Beauty Expert / Trust Guardian / Beauty Explorer

- 15개 축 조합(6C2) 전부에 매핑 테이블을 정의해 **어떤 조합도 결과가 비지 않게** 한다
- 낮은 축은 언급하지 않고 상위 2축을 강점으로 서술한다
- 산식은 `packages/shared/src/` 에 **순수 함수**로 구현되어 있고 단위 테스트가 붙어 있다

## 5. 브랜드 추천과 투표

v1의 AI 이미지 자리를 대체하는 v2의 핵심 가치다.

### 5.1 추천 (개인별)

- 브랜드마다 **추천 대상 DNA**와 **축 친화도**를 지정
- 페르소나 일치 우선 → 상위 2축 친화도 순으로 **브랜드 4개** 선정
- 각 브랜드의 대표 제품을 함께 노출 → 고객을 해당 브랜드 부스로 유도

### 5.2 투표 (전체 공통)

- 팝업 운영 브랜드 **10개 전체**의 제품을 보여주고 **3개 선택**
- **계정당 1회** — 앱 계정 기준으로 중복을 막는다
- 집계는 팝업 운영 성과 지표이자 입점 브랜드 피드백 자료가 된다

### 5.3 운영자가 직접 관리한다

브랜드와 제품은 코드가 아니라 **DB에 있고 `/admin/catalog` 에서 편집**한다.
입점 브랜드가 바뀌거나 제품이 추가돼도 **개발자 없이 현장에서 대응**할 수 있다.

## 6. 데이터·개인정보 정책

| 원칙 | 구현 |
|---|---|
| **얼굴 사진 미수집** | v2에서 촬영·AI 생성 자체를 제거 |
| 앱 계정 식별자 | **SHA-256 해시로만 저장**, 원문을 남기지 않음 |
| 별도 동의 화면 | 없음 — 앱 가입 시 동의로 대체 |
| 결과 URL | 192bit 랜덤 토큰 `/r/{token}` |
| 결과 만료 | 48시간 후 자동 삭제 (설정값) |
| 즉시 삭제 | 결과 페이지에 삭제 버튼 |
| 재방문 이력 | 해시 기준 집계, 개인 식별 정보 없음 |
| 분석 데이터 | 익명 세션 ID 기준 |

**v1 대비 개인정보 리스크가 크게 낮아졌다.** 얼굴 이미지를 저장·전송·생성하지 않으므로
베트남 현지 개인정보 대응 부담과 사고 시 영향 범위가 모두 줄었다.
