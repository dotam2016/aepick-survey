## 1. 지금 무엇이 완성되어 있나

**하노이 팝업 Core Value Zone**의 태블릿 체험과 모바일 후속 페이지입니다.
전 구간이 동작하며, 목업으로 대체된 부분은 **aepick app 연동 한 곳**뿐입니다.

```
[입장] 고객이 PAD 화면의 QR을 스캔
   └→ aepick app 계정과 매칭          ← ★ 여기가 목업 (2장)
[체험] PAD에서 6개 게임 → Beauty DNA 판정 → 브랜드·제품 추천
[종료] PAD에 결과 QR 표시
   └→ 고객이 스캔 → 결과 페이지
[투표] 브랜드 체험 후 같은 페이지에서 제품 3개 투표
[확인] 완료 페이지의 히든 UI로 직원이 재방문 횟수 확인
```

### 기술 스택

| 영역 | 사용 기술 | 비고 |
|---|---|---|
| 서버 | Node 22+, Fastify 5 | TypeScript, ESM |
| DB | **`node:sqlite`** (Node 내장) | 실험적 API. 이관 필요 — 5장 |
| 키오스크 | React 18 + Vite | 정적 빌드, 서버가 함께 서빙 |
| 모바일·어드민 | 서버 사이드 HTML 문자열 | 별도 프론트 빌드 없음 |
| 테스트 | vitest 37개 | 스코어링·페르소나·i18n 정합성 |

### 실행

```bash
npm install
npm run demo          # 빌드 + 서버 (HTTPS, 8787)
npm test
```

단일 프로세스가 키오스크·API·모바일·어드민을 **모두 한 포트**에서 서빙합니다.

## 2. ★ 가장 중요 — aepick app 연동 지점

**여기 하나만 실제 구현으로 바꾸면 됩니다.** 나머지 코드는 손댈 필요가 없습니다.

파일: **`server/src/identity.ts`**

```ts
export interface IdentityProvider {
  readonly name: string;
  resolve(credential: string): Promise<AppIdentity | null>;
}
```

현재는 `mockProvider`가 들어 있고, 넘어온 문자열을 **검증 없이 그대로** 계정으로 인정합니다.
`identityProvider`를 실제 구현으로 교체하면 끝입니다.

### app 팀과 합의가 필요한 사항

| # | 항목 | 선택지 / 권장 |
|---|---|---|
| 1 | QR을 누가 읽는가 | (a) app 내장 스캐너 (b) 폰 카메라 → 딥링크로 app 실행 |
| 2 | 신원 증명 방식 | **서명된 토큰(JWT) 권장** — 아래 경고 참고 |
| 3 | 전달 가능한 필드 | 필수: 사용자 식별자 / 선택: 선호 언어 |
| 4 | 완료 푸시 가능 여부 | 있으면 좋음. 없어도 QR로 완결됨 |

> ⚠️ **평문 user id를 그대로 받으면 안 됩니다.**
> 타인의 id를 넣어 **재방문 횟수를 조작**하거나 **남의 투표 자격을 소진**시킬 수 있습니다.
> 서명 토큰을 검증해 `sub`를 사용자 식별자로 쓰는 방식을 권합니다.

### QR이 담는 주소

```
https://<호스트>/p/<12자리 페어링 코드>
```

현재는 이 주소가 **목업 웹 페이지**를 엽니다.
실제로는 이 자리를 app 딥링크로 바꾸거나, app이 코드만 읽어 `claim` API를 직접 호출하면 됩니다.

### 개인정보 처리

`visitorIdOf()` 가 계정 식별자를 **SHA-256 해시**해 저장합니다. 원문은 DB에 남지 않습니다.
`VISITOR_HASH_SALT` 를 **운영 환경에서 반드시 변경**하세요. 바꾸면 기존 방문 이력과 연결이 끊깁니다.

## 3. API 명세

공통 응답 형식:
```json
{ "ok": true,  "data": { ... } }
{ "ok": false, "error": { "code": "...", "message": "..." } }
```

### 3-1. 페어링 (체험 시작)

| 메서드 | 경로 | 호출자 | 설명 |
|---|---|---|---|
| POST | `/api/pairings` | PAD | 일회용 코드 발급. `{deviceId}` → `{code, url, qrPngUrl, expiresAt, mocked}` |
| GET | `/api/pairings/:code` | PAD | 폴링. `{status: pending\|claimed\|expired}` · claimed면 `{sessionId, language, visitCount}` |
| POST | `/api/pairings/:code/claim` | 폰/app | `{credential, language}` → `{sessionId, visitCount}` |
| POST | `/api/pairings/cancel` | PAD | `{deviceId}` — 고객 이탈 시 코드 폐기 |
| GET | `/p/:code` | 폰 | 목업 페어링 페이지 (실제로는 app이 대체) |

**동시성 설계 (PAD 10대 전제)**

- 코드는 **기기마다** 발급됩니다. 고정 QR이면 두 명이 동시에 찍었을 때 어느 PAD의 체험자인지 판별할 수 없습니다.
- 클레임은 `UPDATE ... WHERE status='pending'` 의 **변경 행 수로 승자를 가립니다.** 동시 요청 10건 중 정확히 1건만 성공하는 것을 검증했습니다.
- 같은 PAD가 코드를 재발급하면 이전 코드는 즉시 `expired` 됩니다.
- TTL 3분. 만료분은 60초 주기로 정리합니다.

> **이관 시 주의**: 이 원자성은 `node:sqlite`의 단일 프로세스 직렬 실행에 기대고 있습니다.
> 서버를 여러 인스턴스로 늘리면 **트랜잭션이나 조건부 UPDATE의 원자성을 DB 레벨에서 보장**해야 합니다.
> PostgreSQL이면 같은 `UPDATE ... WHERE` 패턴으로 그대로 동작합니다.

### 3-2. 체험

| 메서드 | 경로 | 설명 |
|---|---|---|
| PATCH | `/api/sessions/:id/language` | 언어 확정 |
| POST | `/api/sessions/:id/answers/:coreKey` | 게임 답변. coreKey ∈ `repick, value, care, trend, localFit, trust` |
| POST | `/api/sessions/:id/complete` | 점수 확정 → 페르소나 → 결과 토큰 · QR · 추천 브랜드/제품 |
| GET | `/api/stats/today` | 대기화면 통계 |
| POST | `/api/events` | 행동 로그 (배열 전송) |

> **세션 생성 라우트는 없습니다.** 세션은 오직 페어링 클레임으로만 만들어집니다.
> v1의 익명 `POST /api/sessions` 는 QR 없이 체험 기록을 만들어 방문 집계와 투표 자격을 우회할 수 있어 제거했습니다.

### 3-3. 결과

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/results/:token` | 페르소나·점수·추천 브랜드/제품·쿠폰 |
| DELETE | `/api/results/:token` | 고객 요청 즉시 삭제 |
| GET | `/r/:token` | 모바일 결과 페이지 (HTML) |

결과는 `RESULT_TTL_HOURS`(기본 48) 후 만료되며 10분 주기로 정리됩니다.
추천 제품은 **체험 시점에 확정된 것을 되살립니다.** 그 사이 카탈로그가 바뀌어도 발급된 결과는 고정입니다.

### 3-4. 투표

| 메서드 | 경로 | 인증 | 설명 |
|---|---|---|---|
| GET | `/api/vote/:token/options` | — | 운영 브랜드 전체와 제품, 기투표 여부 |

## 4. 데이터 모델

```
visitors ──< sessions ──< answers
   │            │
   │            └──< results ──< votes
   │
   └── (재방문 횟수)

pairings  (device_id, code, status, → session_id)
brands ──< brand_products
devices, events
```

| 테이블 | 역할 | 특기 사항 |
|---|---|---|
| `visitors` | app 계정별 방문 이력 | **id는 해시**. `visit_count` — 첫 방문이 1 |
| `pairings` | 일회용 코드 | `UNIQUE(code)`, 상태 전이 pending→claimed/expired |
| `sessions` | 체험 1회 | `visitor_id`로 계정에 귀속 |
| `answers` | 게임 답변 | `UNIQUE(session_id, core_key)` |
| `results` | 결과 토큰 | 만료·삭제 관리 |
| `votes` | 제품 투표 | **`UNIQUE(visitor_id)` — 계정당 1회** |
| `brands` / `brand_products` | 카탈로그 | 다국어 필드는 JSON 문자열 |
| `events` | 행동 로그 | 분석·감사 추적 |

다국어 필드(`tagline`, `name`)와 배열 필드(`persona_tags`, `product_ids`)는 **JSON 문자열**로 저장돼 있습니다.
PostgreSQL로 옮기면 `jsonb`로 바꾸는 것을 권합니다.

## 5. 인프라 이관 시 고려사항

### 5-1. DB — 가장 먼저 할 일

현재 `node:sqlite`는 **Node 실험적 API**이며 기동할 때마다 경고를 출력합니다.
운영에는 적합하지 않으므로 **PostgreSQL 이관**을 권합니다.

| 항목 | 현재 | 이관 시 |
|---|---|---|
| 드라이버 | `node:sqlite` (동기) | `pg` (비동기) — **모든 쿼리 호출부가 async로 바뀝니다** |
| JSON 필드 | TEXT | `jsonb` |
| 원자적 클레임 | 단일 프로세스 직렬 | `UPDATE ... WHERE` 그대로 유효 |
| 스키마 | `server/src/db.ts` 한 파일 | 마이그레이션 도구 도입 권장 |

DB 접근이 `db.prepare(...).run/get/all` 로 통일돼 있어 **얇은 어댑터 한 겹**으로 교체 가능합니다.

### 5-2. 규모 — PAD 10대 기준

| 항목 | 수치 | 비고 |
|---|---|---|
| 폴링 부하 | 약 **7 req/s** | 10대 × 1.5초 간격 |
| 체험당 API | 약 12회 | 페어링·답변 6회·완료 등 |
| 일 세션 | 수백 건 규모 | 팝업 운영 기준 |

부하 자체는 작습니다. 다만 **폴링을 SSE나 WebSocket으로 바꾸면** 트래픽과 지연이 함께 줄어듭니다.

### 5-3. 기기 설정 — 현장 작업

**PAD마다 서로 다른 기기 ID가 필요합니다.** 같은 ID를 쓰면 페어링 코드가 서로를 무효화해 체험이 끊깁니다.

```
최초 1회, 각 PAD의 브라우저에서
   http://<서버>:8787/?device=PAD-03
로 열면 localStorage에 저장됩니다. 이후에는 파라미터 없이 열어도 유지됩니다.
```

미설정 기기는 임의 ID를 자동 부여받아 최소한 서로 구분은 됩니다.

### 5-4. 환경 변수

| 변수 | 기본값 | 운영 시 |
|---|---|---|
| `PORT` | 8787 | |
| `HTTPS` | — | `1`이면 자체 서명 인증서. 정식 인증서 사용 시 불필요 |
| `TUNNEL` | — | `1`이면 프록시 뒤 모드 + 관리자 키 임의 생성 |
| `PUBLIC_BASE_URL` | 요청 호스트에서 유추 | **로드밸런서 뒤에서는 명시 권장** |
| `ADMIN_KEY` | `aepick-admin` | **반드시 변경** |
| `STAFF_PIN` | `1234` | **반드시 변경** |
| `VISITOR_HASH_SALT` | `aepick-dev-salt` | **반드시 변경** (바꾸면 방문 이력 연결 끊김) |
| `RESULT_TTL_HOURS` | 48 | |

`trustProxy: true` 로 설정돼 있어 `X-Forwarded-Proto`를 신뢰합니다. QR 주소가 스킴을 맞추기 위함이며, **신뢰할 수 있는 프록시 뒤에서만** 사용해야 합니다.

### 5-5. 남은 보안 과제

| 항목 | 현재 상태 | 필요한 조치 |
|---|---|---|
| app 신원 검증 | **없음 (목업)** | 서명 토큰 검증 — 2장 |
| 투표 API | 토큰만 알면 호출 가능 | 결과 토큰이 24바이트 난수라 추측은 어렵지만, 세션 바인딩 강화 여지 있음 |
| 직원 PIN | 단순 비교, 시도 제한 없음 | **무차별 대입 제한** 필요 |
| 사은품 중복 수령 | 지급 시각만 기록 | **미결 — 아래 6장** |
| 어드민 인증 | 단일 공유 키 | 계정별 인증 권장 |
| 요청 속도 제한 | 없음 | 공개 노출 시 필수 |

## 6. 미결 사항 (운영팀 결정 대기)

### 6-1. 사은품 중복 수령 방지 ⚠️

현재 구조로는 **완료 화면 스크린샷으로 중복 수령이 가능합니다.** 직원이 육안으로 구분할 수 없습니다.

지금 구현된 것: 지급 시각 기록 + 재지급 시 `already_claimed` 반환.
`votes.reward_claimed_at` / `reward_staff` 컬럼이 이미 준비돼 있습니다.

검토 가능한 방향:
- 완료 화면에 **서버 시각 기반 동적 요소**(수 초마다 바뀌는 코드·색)를 넣어 스크린샷을 무력화
- 직원 단말에서 **QR을 역으로 스캔**해 지급 처리
- 사은품 수령용 **일회용 코드**를 별도 발급

### 6-2. 투표 시점 통제

현재는 결과 페이지에서 **곧바로** 투표로 갈 수 있습니다.
스펙 8번의 의도는 **브랜드를 체험한 뒤** 투표하는 것이므로, 필요하면 직원 코드 입력이나 시간 잠금을 넣어야 합니다.

### 6-3. 다국어

- 브릿지·종료 이미지 7장이 **한국어 전용**입니다 (디자이너 가이드 5장 참고)
- 베트남어 문구는 **기계 번역 상태**입니다. `packages/shared/src/i18n/vi.json` 의 `_note: "[감수 필요]"` — **현지 감수 필요**
